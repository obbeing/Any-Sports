# 장애 보고서 02: 웹 서비스(web 컨테이너) 중단

| 항목 | 내용 |
|---|---|
| 장애 유형 | 서비스 중단 (백엔드 컨테이너 정지, 테스트 장애) |
| 발생 시각 (KST) | 2026-11-23 22:36:44 |
| 탐지 시각 / 탐지 방법 | 22:37:16 / Zabbix 웹 시나리오 점검 실패 → 경보 `Any-Sports 사이트 응답 실패` (High) |
| 탐지 지연 | 약 32초 (점검 주기 30초) |
| 복구 시각 | 22:40:33 (web 컨테이너 재기동) |
| 총 중단 시간 | 약 3분 49초 |
| 심각도 | 높음 (사이트 전체 접속 불가) |

## 1. 재현 방법
`web`(Flask/Gunicorn) 컨테이너를 중지했다.
```
docker compose stop web
```
Nginx와 DB 등 나머지 컨테이너는 그대로 동작한다.

## 2. 탐지
- Zabbix 웹 시나리오(`AnySports`, 30초 주기)가 `http://nginx/`에 접속하다가 실패해 경보를 발생시켰다. (22:37:16, 경보 지속 시간 표시 1분 18초 시점의 화면을 증적으로 보관)
- `docker compose ps`에서 `sports-web`이 목록에서 사라진 것을 확인했다.
- Nginx 로그에서 오류를 확인했다.

## 3. 영향
Nginx 로그에서 확인한 같은 장애의 서로 다른 증상:

| 시각 (UTC) | 상태 | 내용 |
|---|---|---|
| 13:37:16 | 499 | Zabbix 점검 요청이 응답을 받지 못해 클라이언트가 먼저 연결을 끊음 |
| 13:37:35 | 502 | `connect() failed (113: No route to host)` |
| 13:37:48 | 504 | `upstream timed out (110: Connection timed out)` (사용자 curl 요청) |

사용자는 즉시 오류 화면이 아니라 연결 대기 후 504(Gateway Timeout)를 받았다. 컨테이너가 중지되면 그 주소에서 응답이 없어서, 이전에 겪은 `Connection refused`(즉시 502)와 달리 시간 초과로 나타난다. 같은 원인이라도 502, 504, 499가 섞여 나타나므로 오류 코드만으로 원인을 단정하면 안 된다.

## 4. 원인 분석
`docker compose ps`에서 `sports-web` 컨테이너가 없었고, web 로그 마지막 줄이 `Shutting down: Master`(22:36:44)였다. Nginx는 정상, 업스트림(web)이 응답하지 않는 상태로 판단했다.

## 5. 조치와 복구
`docker compose start web`으로 컨테이너를 재기동했다 (22:40:33, gunicorn 정상 기동 로그 확인).
이번에는 컨테이너 IP가 바뀌지 않아 Nginx 재시작은 필요하지 않았다. 반면 이전에 컨테이너를 새로 만들었던(재배포) 사례에서는 Nginx가 옛 IP를 계속 사용해 502가 발생했고 Nginx 재시작으로 복구했다.

## 6. 복구 확인
- `curl http://localhost:8080/` → 200
- Zabbix 경보 RESOLVED 시각: (화면 확인 후 기입)

## 7. 개선점
- Nginx의 백엔드 연결 대기 시간이 길어(기본 60초) 장애 시 사용자가 오래 기다린다. `proxy_connect_timeout`을 짧게 줄이고 점검 오류 시 안내 페이지를 보여 주도록 개선한다.
- `restart: unless-stopped`는 사람이 직접 중지한 컨테이너를 자동으로 되살리지 않는다. 이 경보는 사람의 개입이 필요하다는 신호이므로 알림(Slack 등) 연결이 필요하다.
- 컨테이너를 재생성하면 IP가 바뀌어 Nginx가 옛 IP를 쓰는 문제가 있다. 이름 해석을 다시 하도록 설정하거나 배포 절차에 Nginx 재시작을 넣는다.
- 한계: 서비스 단위의 중단 경보는 사이트 접속 점검에 의존한다. DB 장애 등 내부 원인은 별도의 점검이 필요하다.
