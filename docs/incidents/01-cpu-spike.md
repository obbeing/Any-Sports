# 장애 보고서 01: CPU 사용률 급증

| 항목 | 내용 |
|---|---|
| 장애 유형 | CPU 자원 포화 (부하 생성기로 재현한 테스트 장애) |
| 발생 시각 (KST) | 2026-11-23 21:55:26 |
| 탐지 시각 / 탐지 방법 | 22:01:24 / Zabbix 경보 `Linux: High CPU utilization (over 90% for 5m)` |
| 탐지 지연 | 약 6분 (경보 조건이 "5분 지속"이라 그만큼은 필연) |
| 부하 종료 시각 | 22:03:26 (480초 경과 후 자동 종료) |
| 복구 확인 시각 | 22:04:24 (Zabbix 경보 RESOLVED) |
| 심각도 | 낮음 (Warning) |

## 1. 재현 방법
`scripts/fault_cpu.py`로 12개 워커 프로세스가 480초 동안 CPU를 사용하도록 했다.
```
docker compose --profile tools run --rm fault-cpu --seconds 480
```
부하 프로세스는 우선순위를 낮춰(nice 10) 실행했다. 감시 대상은 Docker가 동작하는 WSL2 리눅스 VM이다.

## 2. 탐지
- Zabbix가 CPU utilization을 수집하다가 90% 초과가 5분 지속되자 Warning 경보를 발생시켰다 (22:01:24).
- Grafana `Any-Sports 서버 상태` 대시보드에서 21:55 이후 CPU가 100% 부근으로 유지되는 것을 확인했다.
- `docker stats`로 원인 컨테이너를 확인했다: `fault-cpu` 컨테이너가 CPU 1195%(약 12코어)를 사용, 다른 컨테이너는 거의 0~2%.

## 3. 영향
| 구분 | 사이트 응답 시간 (curl, 초) |
|---|---|
| 장애 전 (3회) | 0.281 / 0.205 / 0.210 (평균 약 0.23) |
| 장애 중 (1회, 22:00쯤) | 0.215 |

CPU는 100% 가까이 포화되었지만 사이트 응답 시간은 기준선과 차이가 없었다. 부하 프로세스의 우선순위가 낮아 웹 서비스가 CPU를 우선 할당받았기 때문이다. (측정 1회이므로 참고 값이다.)

## 4. 원인 분석
`docker stats`에서 `fault-cpu` 컨테이너 하나가 CPU 대부분을 사용하고 있음을 확인했다. 서비스 컨테이너(web, nginx, db 등)는 정상 범위였다. 실제 운영 환경이라면 같은 방식으로 원인 프로세스와 컨테이너를 특정한 뒤 조치한다.

## 5. 조치와 복구
이번 시나리오에서는 부하가 480초 뒤 자동 종료되도록 했다. 실제 장애라면 원인 컨테이너를 중지한다 (`docker stop <컨테이너>`).

## 6. 복구 확인
- 22:04쯤 Grafana CPU 사용률이 거의 0%로 내려옴
- 22:04:24 Zabbix 경보 `RESOLVED` (경보 지속 시간 3분)
- 복구 후 응답 시간: (측정 후 기입)

## 7. 개선점
- 경보가 "5분 지속" 조건이라 탐지까지 약 6분이 걸린다. 서비스 영향이 큰 환경이라면 임계값(예: 80% 2분)을 낮추거나 응답 시간 경보를 추가한다.
- CPU 수치만으로 장애로 단정하지 않고 응답 시간까지 확인해야 한다. 이번에는 CPU 포화에도 응답 시간이 유지되었다.
- 한계: 감시 대상은 Docker VM이며, 부하는 낮은 우선순위로 걸었다. 우선순위가 같은 프로세스가 CPU를 차지하는 경우에는 응답 지연이 생길 수 있다.
